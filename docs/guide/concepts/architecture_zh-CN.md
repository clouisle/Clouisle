# 系统架构

本文档概述了 Clouisle 的系统架构，解释不同组件如何协同工作，提供企业级 AI Agent 和知识库平台。

## 架构概览

Clouisle 采用现代化、可扩展的架构，前端、后端和基础设施层之间有清晰的分离。

```
┌─────────────────────────────────────────────────────────────────┐
│                         前端 (Next.js 16)                        │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────────────┐ │
│  │  管理后台 │  │  用户平台 │  │   聊天   │  │  认证 (SSO/登录) │ │
│  └──────────┘  └──────────┘  └──────────┘  └──────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌─────────────────────────────────────────────────────────────────┐
│                        后端 (FastAPI)                            │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────────────┐ │
│  │  Agent   │  │  工作流  │  │  知识库  │  │   用户与团队     │ │
│  │   引擎   │  │   引擎   │  │         │  │     管理        │ │
```

## 技术栈

### 前端层

**框架**: Next.js 16 with App Router
- **开发/构建工具**: Bun 1.0+
- **生产运行时**: Node.js 22 运行 Next.js standalone 服务器（`node server.js`）
- **语言**: TypeScript
- **状态管理**: React hooks + Context API
- **API 客户端**: Axios with custom interceptors

**主要特性**:
- 服务端渲染 (SSR) 以获得最佳性能
- 多个路由组用于不同的用户体验
- 通过服务器发送事件 (SSE) 实现实时更新
- 国际化 (i18n) 支持

### 后端层

**框架**: FastAPI (Python 3.13)
- **ORM**: Tortoise ORM with AsyncPG
- **任务队列**: Celery + Redis
- **向量数据库**: Qdrant
- **LLM 框架**: 基于 LangChain 的聊天、嵌入和文本分块适配器
- **工作流引擎**: 自研 `WorkflowOrchestrator`（LangGraph 仅为声明的依赖，运行时未使用）
- **文档处理**: MarkItDown

**主要特性**:
- 全面使用 async/await 实现高并发
- 所有端点的统一响应格式
- 带 i18n 的全面错误处理
- 为选定的安全相关和变更操作记录审计日志
- 多渠道通知系统

### 基础设施层

**数据库**: PostgreSQL 17（带 `pg_search` 全文搜索）
- 存储所有应用数据（用户、团队、智能体、工作流等）
- ACID 合规性确保数据完整性
- 通过 `pg_search` 扩展实现全文搜索功能

**缓存与队列**: Redis 7
- JWT 是主要认证机制；Redis 保存令牌黑名单，并在配置时支持单会话限制
- Celery 任务代理和结果后端
- 速率限制计数器
- 临时数据缓存

**向量数据库**: Qdrant
- 存储向量检索使用的文档嵌入
- 集合名称使用配置的前缀加嵌入维度（例如 `<prefix>_1536`）
- 知识库会记录嵌入维度；同一知识库中的文档必须使用相同维度
- 高效的向量操作

## 组件交互

### 请求流程

#### 1. 用户请求流程

```
浏览器 → （可选外部反向代理 / Ingress）→ Next.js SSR（node server.js）→ API 请求 → FastAPI 后端
                                                      ↓
                                                 PostgreSQL
                                                      ↓
                                                   响应
```

#### 2. 聊天请求流程（带 RAG）

```
用户消息 → FastAPI → Agent 引擎 → 检索目标
                                  ├── 向量搜索 → Qdrant
                                  ├── 词法搜索 → PostgreSQL/pg_search
                                  └── 可选重排序模型
                                                   ↓
                                          检索到的分块
                                  ↓
                     LLM 适配器 → LLM 提供商 → 响应 (SSE)
```

Agent 使用 `off`、`auto` 或 `agentic` 选择 RAG 行为。知识库检索另有 `vector`、`fulltext` 和 `hybrid` 三种搜索模式，并可选重排序。
#### 3. 文档处理流程

```
上传 → FastAPI → Celery knowledge 队列 → MarkItDown → 文本提取
                                           ↓
                                         分块（按字符）
                                           ↓
                                      生成嵌入
                                           ↓
                         Qdrant 向量 + pg_search 词法索引
                                           ↓
                                状态更新 (PostgreSQL)
```

#### 4. 工作流执行流程

```
触发 → FastAPI → Celery workflow 队列 → 工作流编排器
                                        ↓
                                   节点执行
                         （用户输入/触发器/回答；LLM/Agent/媒体；工具/HTTP/子工作流；检索/文档/文件转 URL；代码/模板/变量/参数转换；条件/分类器/迭代/循环/暂停）
                                        ↓
                                   结果存储
                                        ↓
                                SSE 流（如果实时）
```

## 可扩展性考虑

### 水平扩展

**前端**:
- 无状态 Next.js standalone 实例
- 可扩展到多个副本
- 负载均衡器分配流量

**后端**:
- 无状态 FastAPI 实例
- 可扩展到多个副本
- JWT 请求独立验证；配置时 Redis 用于黑名单/单会话状态

**Celery Workers**:
- 可扩展到多个 worker
- 基于队列的任务分配
- 不同任务类型的独立队列

**Celery Beat**:
- **必须恰好运行 1 个实例**（定时任务）
- 以裸调度器运行，无数据库锁——请保持单实例以避免重复调度

### 垂直扩展

**PostgreSQL**:
- 增加 CPU/RAM 以提高查询性能
- 连接池提高效率

**Redis**:
- 增加内存以扩大缓存
- 持久化以保证持久性

**Qdrant**:
- 增加内存以支持更大的向量集合
- SSD 以加快磁盘 I/O

## 安全架构

### 身份验证与授权

**多层安全**:
1. **前端**: 路由守卫、基于角色的 UI 渲染
2. **后端**: JWT 令牌验证、权限检查和团队成员资格检查
3. **数据库**: 通过应用层过滤实施团队和资源授权；不使用 PostgreSQL RLS

**身份验证方法**:
- 基于密码（使用 bcrypt 哈希）
- SSO（OAuth2、OIDC、SAML、CAS）
- API 密钥（用于程序化访问）

### 数据隔离

**基于团队的多租户**：
- 大多数用户创建的资源以团队为作用域；系统技能和显式共享的工具是例外
- 用户可以是多个团队的成员
- 每个端点分别应用团队、所有权和可见性的授权过滤
- 超级管理员可以访问所有数据

## 审计跟踪

**审计日志**：
- 关键认证、管理和变更操作会被记录；具体覆盖范围取决于端点
- 端点提供快照时记录变更前后状态
- 可用时记录 IP 地址和用户代理数据
- 通过审计日志设置配置保留期

## 性能优化

### 缓存策略

**缓存策略**:
- JWT 访问令牌的有效期由 `session_timeout_days` 安全设置控制（种子值为 30 天；设置缺失时登录端点使用 7 天回退值）；Redis 只保存黑名单条目和可选的单会话状态，不是主要会话存储
- 站点设置（无缓存——每次查找直接读取数据库）
- 速率限制计数器（1 小时 TTL，存储于 Redis）

**数据库索引**:
- 主键（UUID）
- 外键
- 频繁查询的字段（email、username、team_id）

### 异步操作

**后台任务**:
- 文档处理（Celery）
- 邮件发送（Celery）
- 工作流执行（Celery）
- 通知传递（Celery）

**实时更新**:
- 聊天响应的 SSE
- 工作流执行的 SSE
- 当前不提供 WebSocket 支持

## 监控与可观测性

### 日志记录

**应用日志**:
- 结构化 JSON 日志
- 日志级别（DEBUG、INFO、WARNING、ERROR）
- 请求/响应日志
- 错误堆栈跟踪

**访问日志**:
- Next.js standalone 服务器日志（前端；容器只运行 `node server.js`，**不含 Nginx** —— `deploy/nginx/default.conf` 是可选的外部反向代理示例，不在镜像内）
- Gunicorn 访问日志（后端；生产模式通过 `python main.py server --no-reload` 运行 Gunicorn + `uvicorn.workers.UvicornWorker`）
- API 端点使用情况

### 指标

**关键监控指标**:
- 请求速率（请求/秒）
- 响应时间（p50、p95、p99）
- 错误率（4xx、5xx）
- 数据库查询时间
- Celery 任务队列长度
- Celery 任务执行时间
- 内存使用
- CPU 使用

### 健康检查

**端点**:
- `/api/v1/health` — 公开基本健康检查；Compose 使用 Python `urllib.request` 探测，Helm/Kubernetes 使用 HTTP probe
- `/api/v1/admin/observability/system/health` — 管理端可观测性健康检查（CPU/内存/磁盘/数据库/Redis/Worker），需 `admin:dashboard:access` 权限
